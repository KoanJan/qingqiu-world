# Run a Semantic Case

Use this Skill when asked to execute or judge a case under `tests/cases/S/`. The [semantic standard](../../../spec/development/testing/semantic.md) defines verdict authority, calibration, and status; the [evidence standard](../../../spec/development/testing/evidence.md) defines input provenance, isolation, and reports. This Skill turns those rules into a procedure. It does not define a case's product route, scenario format, fixture names, or executor.

1. **Identify the case and its contract.** Find the named case through the [case index](../README.md). Read its README to learn its entry point, prerequisites, assets, commands or Agent actions, and evidence locations. Read its scenario definition for the actual criteria, input, and limits. Check the definition against the semantic standard and run its validator when one exists. Do not change criteria after observing the subject's output.
2. **Establish inputs and limits.** Before any live product run, require all six environment variables named in the [semantic standard](../../../spec/development/testing/semantic.md#result-limits-and-execution-boundary): three for the LLM and three for the embedding provider, even if this case uses only one provider type. Check them by presence without printing values, along with the case's other declared environment, time and retry limits, and any model-call limit. If one is missing or blank, do not start the product; retain a diagnostic `ERROR` run naming the missing variables. Use only operator-supplied environment values, without substituting another source. Provider budget controls govern spending, not the test verdict.
3. **Calibrate when useful for judgment.** Reference claims and original evidence may check whether a judge can distinguish supported, contradicted, and insufficient-evidence outcomes. For blind calibration, keep expected labels and the subject output away from the judge until calibration is complete. Save any calibration with the local run; if it shows the judge cannot apply the categories reliably, use another judge or record `INCONCLUSIVE`. If calibration is skipped where it matters to interpretation, record that limitation.
4. **Capture the product behavior.** Follow the case README's actual execution path, whether it uses a runner or Agent actions. Start with isolated case data, exercise the documented product entry point using current local source, and preserve the real output, original inputs, and mechanical observations in that case's run record. Record setup or execution failure as `ERROR`, failed mechanical assertions as `FAIL`, and a completed capture awaiting semantic judgment as `INCONCLUSIVE`. A capture cannot establish `PASS`. If the case provides capture validation, run it before judgment.
   - Scripted cases pause for an AI stop review when the subject sends a new message or when two 30-second state polls show the same ongoing state. Keep the runner process alive. Read the printed `data/stop_review_request.json`, then write `data/stop_review_response.json` with that request's `request_id`, `decision` (`stop`, `continue`, or `uncertain`), and a brief `reason`. Write the response atomically so the runner does not read a partial file. For a `reply` review, decide only whether the full reply sequence expresses that this request is finished; do not judge whether it is correct. For a `stalled` review, inspect the included state and new log excerpt, and the full `server.log` if the excerpt is truncated, before deciding whether observation should continue. An uncertain reply continues to state polling. The scenario timeout remains the upper bound.
   - The runner saves the visible messages, database evidence, and `server_pre_stop.log` before stopping its owned server. Judge against that pre-stop evidence; server shutdown may alter Work status. `stop_monitor.json` records the stop reason, state polls, and AI stop reviews. These reviews decide capture duration, not the semantic verdict.
5. **Judge every criterion against the evidence.** Prefer a session that did not perform capture for an independent judgment. Give it the scenario criteria, original evidence, captured output, and relevant run artifacts, without the README's operator-only expected labels. Evaluate each required and forbidden criterion even if a mechanical failure has already fixed the run status. Explain what was observed and cite the supporting artifact. Distinguish an input's availability from evidence that the subject retrieved or used it; do not turn a missing trace into an invented account of what the subject did. Preserve captured mechanical facts; a judge cannot soften a mechanical `FAIL` or `ERROR`. If judgment occurs in the capture session or after expected labels were exposed, record that limitation.
6. **Finalize and report.** Write the judge identity, rationale, criterion observations and evidence, limitations, and any deviations into the case's result and report while keeping captured facts intact. Set the report's `Status:` line to the final result status; do not leave its capture-stage status in place. For an executable case, run its required final result validator using the documented command and exit meanings; otherwise check the final record against the semantic and evidence standards and any case-specific checks. Report the verdict, run directory, evidence, and unverified criteria. Stop at judgment unless the user separately asks for diagnosis or repair.

The case README is an operator guide and may contain expected labels. A separate judge receives only the materials needed to assess the criteria; reading the README or its labels makes the judgment non-blind and must be recorded. Case-specific execution instructions belong with that case, not in this Skill.
