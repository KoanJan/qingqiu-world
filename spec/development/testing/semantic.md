# Model-Dependent Semantic Scenarios

Apply the [test contract and risk selection](README.md) first; use [evidence and reports](evidence.md) for input provenance, isolation, and reporting.

A semantic scenario names a model-dependent behavior, declares its criteria before any model run, and records a bounded qualitative judgment against the original evidence. The rules below are defined once across this standard and [evidence and reports](evidence.md); the shared [S-track Skill](../../../tests/cases/S/SKILL.md) turns them into execution steps, while each case README supplies its own paths, data, and examples.

## Roles, Verdict Authority, and Calibration

A run has three roles. **Capture** decides only mechanically checkable facts — missing required records, contradictory product state, and setup failures — and writes them as captured facts; its status is `FAIL` when a mechanical assertion fails, `ERROR` when setup fails, and otherwise `INCONCLUSIVE`. **Calibration**, when used, exercises a judge on reference cases whose conclusions were established independently of it, covering supported, contradicted, and insufficient-evidence examples with misleading or conflicting evidence relevant to the scenario; check false passes as well as false failures, repeat calibration when the judge, criteria, or relevant model behavior changes, and save its results with the local run. **Judgment** evaluates the predeclared criteria against captured output and original evidence. An independent judge works in a session that did not execute capture; a same-session judgment is allowed with its limitation recorded. Only judgment may establish a semantic verdict; capture cannot assign `PASS`, and judgment cannot soften a mechanical `FAIL` or `ERROR`.

An independent judge is an agent or session that did not execute the capture; a same-session judgment is recorded as a limitation. A verdict may be formed in a separate session and transcribed by the capture session: `judge.kind` records where the verdict was formed, and the transcription is recorded in `deviations`. Expected calibration labels are operator material, so give a judge only the claims for a blind calibration. Blindness is recommended, not required: a judge that has already read the labels produces a consistency check rather than evidence of independent judgment, and that limitation is recorded. The judge must inspect the actual model output and original evidence, explain the connection between them, and distinguish observed facts from interpretation. Source availability, observed retrieval, and use in an answer are different facts; an indexed source alone does not prove retrieval. When the subject says "not found", establish whether it reports a failed search or asserts that the source does not exist before calling that statement contradicted. Do not use the subject agent's self-assessment as independent evidence, and do not request a numeric or free-form quality score from a generative model.

Calibration is optional for a test run. When used blind, it must precede observing the subject's output; a later non-blind check no longer establishes independence. Record skipped calibration as a limitation when judge reliability matters to interpretation. If calibration shows the judge cannot apply the categories reliably, seek another judge or record `INCONCLUSIVE`; an unreliable judgment cannot support `PASS`. Calibration need not mean human review of every run.

## Result, Limits, and Execution Boundary

Every live S-case product run requires all six operator-supplied process environment variables: `QINGQIU_TEST_LLM_BASE_URL`, `QINGQIU_TEST_LLM_MODEL_ID`, `QINGQIU_TEST_LLM_API_KEY`, `QINGQIU_TEST_EMBEDDING_BASE_URL`, `QINGQIU_TEST_EMBEDDING_MODEL_ID`, and `QINGQIU_TEST_EMBEDDING_API_KEY`. Check them before starting the product or making provider calls, including for a case that exercises only one provider type. An absent or blank value stops the run as a diagnostic `ERROR`; record missing names only, without printing values or substituting product configuration. A corrected attempt is a new run. Scenario validation, offline contract tests, and judgment of already captured evidence do not start a product run and do not require these credentials.

The test result describes this run's observed product behavior and evidence. `PASS` means every criterion is supported and the required mechanical checks succeeded; `FAIL` means an observed contradiction; `INCONCLUSIVE` means the evidence cannot decide; `ERROR` means setup or execution failed. An Issue's acceptance owner, a PR's review policy, a clean worktree, and provider cost controls do not change that result. Record the tested revision and worktree state for reproducibility. A non-author developer reruns the committed case on the code being reviewed and makes the delivery decision under the [PR review rules](../../collaboration/review.md); an earlier successful run cannot override a later observed product failure. Generated run reports remain local and are not committed.

A run's duty ends at judgment: report the captured evidence and verdict and stop. Product root-cause diagnosis or fix is a separate mandate performed only when the operator asks. A test agent's run does not approve or merge a PR. When a stable scenario becomes mechanically verifiable, move its fixed checks into ordinary automated tests.

## Status by Cause and Machine Interface

A required mechanical record that is absent is `FAIL`; evidence that cannot be read because of tooling is `INCONCLUSIVE`; setup or execution failure is `ERROR`. Call a record required only when the case explains why the tested product path must produce it for the claimed behavior, and review that assertion if the product gains another valid path. An absent trace establishes that no trace was recorded; it does not establish whether an operation was attempted or what it returned. A capture awaiting judgment must not return a passing gate. Final validation requires a completed judge and an observation for every criterion on non-`ERROR` results; only a validated final `PASS` may return zero. A scripted S case must document its capture and final-validation exit meanings in its README or shared case documentation; the [case index](../../../tests/cases/README.md) currently records the shared exit codes. A recorded mechanical failure requires status `FAIL`, so validation must reject any softening of it. A run is the unit of evidence; a rerun is a new run and evidence is never merged across runs.

## Observable Fields

Every numeric or derived field states its source, computation, and unknown value. A model-call limit must say whether it applies to a phase, process, or whole run; an observed count must say which calls it includes. Do not compare an aggregate count with a per-phase bound or present a partial count as a provider total. When the records needed for a count are absent, record `null` or an equivalent unknown and apply the status rule above instead of reporting zero. Do not require a metric that the tested path cannot observe unless that metric is essential to the case's claim. A criterion that depends on an unreadable source cannot `PASS`.

## Result Record

Every semantic result pairs each predeclared criterion with its status, observation, and evidence references. Criterion status is per criterion, so a failed run may contain a satisfied forbidden criterion recorded as `PASS` with an observation that the prohibited behavior did not occur. Mechanical failures are run-level facts: the judge still evaluates and records every criterion, and may not upgrade a mechanical `FAIL`. Record the judge's kind, model, judgment, and rationale, whatever result format the case uses. `independent_agent` means the verdict was formed in a session that did not run capture, and `same_session_agent` means otherwise. A model identifier that cannot be confirmed is recorded as self-reported in `limitations`, with `unverified` used only when none is reported. `supported` applies only when every required criterion is satisfied, `contradicted` when an observed result contradicts one, and `insufficient_evidence` when evidence cannot decide. Record deviations from the written steps with their reasons, separately from limitations that remain unverified or undeclared.

Preserve capture facts in a separate, immutable run artifact before semantic judgment. The result validator pins failures, completed checks, and any measured counts to that capture artifact and does not let judgment change a captured `FAIL` or `ERROR`. Capture validation checks structure and immutable facts; final validation additionally requires a completed judgment for every non-`ERROR` result. The judgment session completes the result and adds every new evidence file to the artifact manifest before referencing it; it may rewrite `report.md` while preserving captured facts. When the capture session transcribes a returned verdict, record that in `deviations` without changing where `judge.kind` says the verdict was formed.

When calibration is used, retain the reference claims, independently established labels, observed judgments, and their provenance in the run evidence. The operator must be able to tell which claims the judge saw and whether it distinguished supported, contradicted, and insufficient-evidence examples. The report language follows the operator's language unless the case README explicitly names one.

## Author and Execute a Semantic Scenario

Follow the [case directory layout](case_directory.md) for each cross-component semantic case. Its README is the operator artifact: how to run it, which data it uses, what outcome to expect, and which evidence and status to inspect, including operator-only expected labels; the shared [S-track Skill](../../../tests/cases/S/SKILL.md) gives the Agent's method without duplicating the scenario's criteria. The directory name identifies the case. A versioned scenario definition owns the case's actual input, criteria, and limits; an executor loads those declared values rather than maintaining a second definition. Track `proposed → reviewed → active → deprecated`: `proposed` has a draft contract, `reviewed` has had its risk, entry, and oracle checked in the [case readiness review](README.md#review-whether-a-case-is-ready), and `active` has a validated definition and implemented capture and result checks. Run a new active case and inspect its complete evidence path before relying on it; a product `FAIL` does not prevent the case from remaining active. Mark a definition `deprecated` when its product contract or evidence path no longer applies. A Markdown definition is acceptable for a case executed entirely by an Agent, but must not be presented as runnable through a script that hardcodes a different definition. Never reuse a case directory name for a different purpose, and advance the definition version when criteria or input facts change.

A scripted S case places its versioned scenario definition at the case root and validates that definition and the final result. For a JSON definition, use `scenario-vN.json` with `version`, `lifecycle`, `required`, `forbidden`, and `limits`, plus the input fields its workflow needs. Each criterion has an `id` and a `condition`; the ID pairs it with its result. Declare only limits the executor actually uses. The filename and validated model identify the JSON format, so a separate `schema_version` field is unnecessary. Keep committed source inputs under the case's `assets/` directory, preserve the exact bytes used in the run, and record their checksum. Do not add a second fixture version label or duplicate its facts in prose fields. Put distinctions that affect the verdict into `required` or `forbidden`. Do not force a fixture, question, result model, or product runner from one workflow onto another. In every case, the README owns the human explanation, product route, data flow, prerequisites, and trigger guidance; the executor owns real calls, isolation, mechanical checks, and resource handling. Do not add declarative fields that the executor neither reads nor checks.

For a scenario that claims an input caused an action or effect, map the stages present in the product path: original input, accepted decision, selected plan, committed effect, and any user-visible output. State where the case stops when later stages are out of scope. Follow the available durable references between stages in scope; sharing an owner, session, or time window does not by itself prove causation. If the path lacks a link needed for the claim, record that limit instead of presenting the chain as established. State which fields are internal instructions, planned content, effective payloads, or completed output, and judge each against its actual role. An internal note need not read like a user-facing message, and a plan alone does not establish that its effect occurred.

Define the relevant set of outcomes before execution. A check for one correct effect must not overlook another relevant effect that violates a forbidden criterion; state whether the case expects at least one, every relevant effect to comply, or exactly one. For time-based behavior, declare the reference timestamp, timezone, tolerance, and handling of calendar rollover; compare actual instants rather than treating a date change alone as an error. Review the criteria against both a valid boundary case and a misleading or mixed result when those cases can arise.

Check applicable mechanical facts before asking for semantic judgment: input provenance, access scope, required state transitions, references, and output structure. Check mechanically decidable forbidden outcomes over the declared result set before judgment; leave meaning that requires interpretation to the judge. For a case that cites a source, check that the source and cited version exist and are accessible; a valid citation alone does not prove that the source supports the claimed meaning.

Validate the scenario before execution with its own validator when one exists, or by checking its declared format and criteria. The capture executor checks the environment and operates the isolated product. The judge reads the validated criteria, captured output, and original evidence, then writes or returns the final judgment; a separate session is preferred, and a same-session judgment is labeled and limited as described above. Mechanical checks and captured output are inputs to judgment, not a semantic `PASS`. An executor may adjust execution steps when the environment or subject behavior requires it, but must record the deviation and its reason in `deviations`; it must not change criteria after seeing the output, quietly modify the tested code, or claim that an unperformed action succeeded.

The shared [S-track Skill](../../../tests/cases/S/SKILL.md) turns these rules into execution steps for every case; it may not relax or extend them. Use the [shared result meanings](evidence.md#result-meanings). A semantic `PASS` establishes only this run's stated behavior; it does not approve a PR or predict another model run. The non-author reviewer reruns relevant cases locally under the [PR review rules](../../collaboration/review.md).

Assess S-track breadth by distinct behaviors rather than case count. Positive and negative inputs for one behavior strengthen its oracle but do not establish breadth across Agent behavior. Add a new scenario only after its real entry point, input preparation, and evidence oracle have been verified; do not fill a target count with display-only cases.
