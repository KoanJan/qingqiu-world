# Local Data During Issue Development

Developer data has two distinct states: an immutable copy of the latest released version, and a writable active copy for committed development changes. The active copy records its released baseline and an ordered `dev.x.<commit>` migration chain in `.dev-data-version.json`; `db_versions` records only released versions. The development revision `x` determines order, and the full Git commit hash identifies the change that introduced that revision.

## Before Running Development Code

- Enable developer data management explicitly and identify the source repository. The Go development launcher and Electron development launcher build a binary stamped with the checked-out commit. Direct server startup must use a binary built through the same path. A user installation runs only the release path and does not require Git.
- Keep one verified, immutable baseline from the latest released version. It must contain the complete data collection, including SQLite and file resources. Baselines, checkpoints, staging, and quarantine live outside the active `DATA_ROOT`. Configured file roots outside `DATA_ROOT` must be included in a coordinated data collection; if that cannot be guaranteed, automatic management stops.
- On first use, import a verified released-data backup or initialize genuinely fresh data with the matching released schema. An existing active directory is not a baseline merely because its `db_versions` value equals the released version. If the active directory has already been changed by development code and no trusted released backup exists, stop and obtain a trustworthy baseline before continuing.
- To import an existing released-data directory on first use, set `DEV_BASELINE_SOURCE` to that directory when running the developer launcher. The manager copies and verifies it, then quarantines the previous active directory before using a new development copy. Do not point this variable at active development data.
- The initial backup must be at the current release unless the target release tag supports isolated release migration execution. The historical v0.1.21 server did not provide that execution mode, so a developer starting with this implementation needs a trustworthy 0.1.21 backup or a genuinely fresh baseline.
- Develop against a committed work-in-progress change. Automatic management only runs on committed code: a dirty worktree, including untracked files, or a binary that was not built through the stamped launcher stops startup before any migration is applied. Commit the work once and amend that commit between iterations. Commits that leave the persistent-data code paths and development migration files untouched keep the chain and reuse active data; a persistent-data code change requires a registered step, and editing a step file, the registry, or rewriting step commits changes step identity and replays the affected steps from a checkpoint or the released baseline. Keep scratch files outside the repository.
- Do not automatically manage uncommitted code changes or data written by them. A clean worktree later does not certify that such data belongs to the last recorded commit. The developer must restore or provide a trustworthy committed-version data state before automatic management resumes.

## After Pulling or Rebasing

- Determine the target development migration chain from the checked-out Git history and the current migration registry. Every committed schema, persistent data, or data-directory change needs a registered development step. Ordinary commits without such changes do not increment `x`.
- If the active chain is an exact prefix of the target chain, run only the missing steps from a staged copy of active data. If the chains differ, find their longest common `(x, commit)` prefix and rebuild from its verified checkpoint, an earlier verified checkpoint, or the released baseline. A same-number step from a different commit is a different step. A shorter target chain also requires a rebuild; never edit version metadata to simulate a rollback.
- Quarantine the old active directory before switching to a validated replacement. Do not merge ordinary writes from the old copy into a rebuilt copy. A checkpoint represents the committed migration state and ordinary data as they existed when that consistent checkpoint was made; later writes are not included retroactively.
- If the repository is dirty, the migration order cannot be determined, a manifest is corrupt, or the running binary does not match the checkout, stop automatic migration and preserve the data. A developer can manually handle uncommitted work, then resume from a trustworthy state.

## When a New Version Is Released

- Before checking development migrations, upgrade a staged copy of the previous immutable release baseline with the **final released code**. Run every required release step, validate SQLite and files, and freeze the new release baseline. The release upgrade never runs on the old development active directory and never replays development migrations.
- Quarantine the old active copy and derive new `dev.0` data from the new baseline. The old baseline's development chain and checkpoints are invalid under the new baseline. Keep the previous baseline until recovery from the new one has been verified.
- Before publication, fold the final development schema and data effects into the next release migration and remove the old baseline's development steps from the released code. The release migration must work directly from the previous released baseline.

The data manager locks the collection for the server lifetime. Staged copies and completion manifests protect against interrupted migrations and switches; only validated, complete copies may be used. SQLite WAL and all configured file roots are part of the same recovery decision.
